### 3.3 Qdrant 502 根因

知识库上传时出现的 502 发生在 embedding 之前：

1. Open WebUI 调用本机 Qdrant `collection_exists`。
2. 系统 HTTP 代理接管 loopback 请求。
3. 代理返回空的 502 响应。

修复位置：

- `backend/open_webui/retrieval/vector/dbs/qdrant.py`
- `backend/open_webui/retrieval/vector/dbs/qdrant_multitenancy.py`

现在仅对 `localhost`、`127.0.0.1` 和 `::1` 禁用环境代理；远程 Qdrant 继续保留原代理行为。

问题表现：聊天侧边栏悬浮预览在 Chromium 108 中下边框和整体轮廓不清晰，现代 Chrome 中正常。

- 浅色主题使用 `gray-200`。
- 深色主题使用 `gray-700`。
- 保持原定位、尺寸、圆角和阴影不变。

验证：

- 生产构建成功。
- Chromium 108.0.5359.29 与 Chrome 151.0.7922.71 的计算样式均为 `1px solid rgb(228, 228, 228)`、`16px` 圆角。

## 5. PDF 知识文件与内容提取

### 5.1 PDF 支持情况

当前管理后台支持把 PDF 作为知识文件处理。需要区分两类 PDF：

- 文本型 PDF：内置提取器通常可以直接读取文本。
- 扫描型/图片型 PDF：需要开启“PDF 图像提取（使用文字识别）”或选择带 OCR 的外部提取引擎。

“PDF 加载模式”的含义：

- 页模式：每页形成独立文档，便于保留页边界和页码语义。
- 单模式：将页面合并为一个文档后再切分，适合连续正文。

本轮确认了配置和能力入口，没有对指定 PDF 做完整上传、OCR、切分、索引和问答闭环测试。

### 5.2 内容提取引擎

界面可选项包括：

- 默认：Open WebUI 内置解析流程。
- 外部：调用自定义内容提取服务。
- Tika：Apache Tika 通用文档解析。
- Docling：面向 PDF/Office 的结构化解析。
- Datalab Marker API：将复杂 PDF 转为结构化 Markdown。
- Document Intelligence：云端版面与表格识别服务。
- Mistral OCR：OCR/文档理解服务。
- PaddleOCR-VL：PaddleOCR 视觉语言文档解析。
- MinerU：PDF 版面、公式、表格和正文结构化解析。

选择非默认引擎通常还需要对应服务地址、API Key 或本地依赖；下拉框中出现选项不代表服务已经配置完成。

## 6. Embedding 与检索排查

### 6.1 为什么切换 OpenAI 引擎后模型自动变化

这是前端当前的明确行为，不是百炼返回或自动识别的结果。

`src/lib/components/admin/Settings/Documents.svelte` 在切换引擎时设置：

- `openai` -> `text-embedding-3-small`
- `azure_openai` -> `text-embedding-3-small`
- 本地 SentenceTransformers -> `sentence-transformers/all-MiniLM-L6-v2`

因此选择 OpenAI-compatible 百炼后，需要再次手动把模型名改为 `text-embedding-v4`。

### 6.2 OpenAI-compatible 调用限制

`backend/open_webui/retrieval/utils.py` 的通用 OpenAI embedding 请求默认只发送：

```json
{
  "input": ["..."],
  "model": "text-embedding-v4"
}
```

当前实现没有发送 `dimensions`，因此 v4 使用服务端默认 1024 维；也没有区分百炼原生 API 的 `query`/`document` 文本类型。若需要 `text_type` 或 `instruct`，需要增加百炼原生接口适配，不能只靠现有 OpenAI-compatible 配置。

百炼官方限制 v4 单批最多 10 条，因此当前配置的 `Embedding Batch Size` 应保持 `<= 10`。

### 6.3 `text-embedding-v4` 实测

为避免把本地知识文件正文发送给外部服务，本轮只使用现场生成的非私密合成语料：10 个文档片段、6 个查询，共调用兼容接口 2 次。

接口结果：

| 项目 | 结果 |
| --- | --- |
| HTTP | 200 |
| 返回模型 | `text-embedding-v4` |
| 默认维度 | 1024 |
| 向量范数 | 全部 1.0 |
| 正向查询 Top-1 | 5/5，100% |
| MRR | 1.0000 |
| Token | 411 |
| 两批总耗时 | 17.502 秒 |

Top-1 余弦相似度：

| 查询 | 正确文档得分 |
| --- | ---: |
| ES + Redis 多轮上下文检索 | 0.8201 |
| 2024/2025 中国 GDP | 0.8285 |
| 美团 GPU 向量检索 | 0.8909 |
| 扫描 PDF OCR 入库 | 0.7738 |
| 英文查询 ES + Redis 中文文档 | 0.8036 |

结论：模型输出和语义排序正常；相比本地 MiniLM，当前百炼请求的网络延迟明显，但单次小样本不能代表长期吞吐。

测试使用的 API Key 不记录在文档、项目记忆或 Git 中。由于凭据曾通过聊天明文传递，应在百炼控制台轮换。

### 6.4 当前 Qdrant 数据风险

2026-08-05 只读检查结果：

| 物理集合 | 维度 | 点数 | 发现 |
| --- | ---: | ---: | --- |
| `open-webui_files` | 1024 | 18 | 15 条 v4，3 条 `qwen3.7-text-embedding` |
| `open-webui_knowledge` | 3 | 0 | 遗留空集合，维度明显不适用于当前 embedding |

`ES + Redis 上下文检索优化简短方案.docx` 的 3 个分块使用 `qwen3.7-text-embedding`，而其他 15 个分块使用 `text-embedding-v4`。即使两个模型恰好都是 1024 维，它们也不属于同一语义空间，不能用 v4 查询向量进行可靠比较。

多租户 Qdrant 适配会把所有 `file-*` 逻辑集合映射到同一个 `open-webui_files` 物理集合。因此：

- 删除或重建单个知识库不一定会重建物理集合。
- 从本地 MiniLM 的 384 维切换到 v4 的 1024 维时，必须确保物理集合也按目标维度重建。
- 同一物理集合内必须统一模型、维度、归一化和文本预处理策略。

### 6.5 截图中“能检索到”的含义

聊天截图显示调用了：

- `search_knowledge_bases`
- `search_knowledge_files`
- `view_knowledge_file`

这些工具主要负责按知识库/文件元数据查找并直接读取内容，不能单独证明向量召回成功。真正执行语义向量检索的内置工具是 `query_knowledge_files`。

后续验证必须记录 `query_knowledge_files` 的 Top-K、分数、文件 ID、分块起始位置和 embedding 配置，避免把“按名称找到文件”误判成“向量检索准确”。

## 7. 推荐的数据修复顺序

以下操作尚未执行，涉及现有向量数据，执行前必须备份并获得明确确认：

1. 确定唯一 embedding 模型。若优先速度和离线能力，继续使用 MiniLM；若使用百炼，固定为 `text-embedding-v4`。
2. 记录目标维度：MiniLM 为 384，v4 当前兼容接口默认是 1024。
3. 导出或备份现有 Qdrant 数据与知识库文件映射。
4. 停止写入后，重建 `open-webui_files` 与 `open-webui_knowledge` 的物理集合，确保维度正确。
5. 使用同一模型重新上传或重新索引全部文档；不要保留旧模型生成的点。
6. 将百炼批大小设置为不超过 10。
7. 用固定问题集调用 `query_knowledge_files`，记录 Recall@K/MRR、延迟和误召回。
8. 验证完成后再开放正常写入。

不要只修改模型下拉框后继续使用旧向量；模型、维度或预处理任一项改变，都应重新索引。
